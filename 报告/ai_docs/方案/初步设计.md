
# SSH Forward 全平台 SSH 端口转发工具设计文档

## 1. 项目概述

### 1.1 项目名称

**SSH Forward**

命令行名称：

```bash
ssh-forward
```

桌面端名称：

```text
SSH Forward
```

### 1.2 产品定位

SSH Forward 是一个专门用于管理 **SSH 端口转发 / SSH Tunnel** 的跨平台工具。

目标不是替代 Xshell、Termius、MobaXterm 等完整 SSH 客户端，而是把：

```text
SSH 连接
+
端口映射
+
自动重连
+
GUI 管理
+
CLI 管理
```

这一件事情做到简单、稳定、可复现。

主要支持：

```text
Windows
Linux
macOS
```

后期可以考虑：

```text
Android
iOS
```

---

# 2. 核心使用场景

典型服务器：

```text
192.168.6.240
```

服务器上运行：

```text
Jupyter      127.0.0.1:8888
RStudio      127.0.0.1:8787
MySQL        127.0.0.1:3306
TensorBoard  127.0.0.1:6006
```

用户希望通过 SSH 将这些端口映射到自己的电脑：

```text
127.0.0.1:18888 → SSH → 127.0.0.1:8888
127.0.0.1:18787 → SSH → 127.0.0.1:8787
127.0.0.1:13306 → SSH → 127.0.0.1:3306
127.0.0.1:16006 → SSH → 127.0.0.1:6006
```

等价于：

```bash
ssh -N \
  -L 127.0.0.1:18888:127.0.0.1:8888 \
  -L 127.0.0.1:18787:127.0.0.1:8787 \
  -L 127.0.0.1:13306:127.0.0.1:3306 \
  -L 127.0.0.1:16006:127.0.0.1:6006 \
  ym@192.168.6.240
```

SSH Forward 将上述复杂命令抽象成 GUI 中的：

```text
iyun240                    ● Connected

Jupyter
127.0.0.1:18888
        ↓
127.0.0.1:8888
[Open] [Stop]

RStudio
127.0.0.1:18787
        ↓
127.0.0.1:8787
[Open] [Stop]
```

# 3. SSH 转发类型

软件设计上支持三类 SSH forwarding。

## 3.1 Local Forward

SSH 参数：

```bash
-L
```

主要场景：

> 访问服务器内部服务。

例如：

```text
本机 127.0.0.1:18888
        ↓
SSH Server
        ↓
远端 127.0.0.1:8888
```

对应：

```bash
ssh -L 127.0.0.1:18888:127.0.0.1:8888 user@server
```

这是 SSH Forward 第一版最重要的功能。

---

## 3.2 Remote Forward

SSH 参数：

```bash
-R
```

例如：

```text
服务器 127.0.0.1:9000
        ↓
SSH
        ↓
本机 127.0.0.1:8000
```

对应：

```bash
ssh -R 127.0.0.1:9000:127.0.0.1:8000 user@server
```

使用场景包括：

```text
开发服务临时暴露给远程服务器
远端访问本机 API
远程调试
反向代理
```

---

## 3.3 Dynamic Forward

SSH 参数：

```bash
-D
```

建立 SOCKS5 代理：

```text
127.0.0.1:1080
```

对应：

```bash
ssh -D 127.0.0.1:1080 user@server
```

第一版可以不实现，第二阶段加入。

# 5. 为什么配置文件建议使用 JSON

结论：

**完全可行，而且推荐。**

对于 SSH Forward 这种 GUI 程序，JSON 比传统 `ssh_config` 更适合作为程序内部数据模型。

优点：

```text
结构明确
支持数组
支持嵌套
跨平台
语言无关
GUI 修改方便
容易验证
容易做版本升级
容易导入导出
容易备份
容易同步
```

例如：

```json
{
  "hosts": [
    {
      "id": "iyun240",
      "name": "iyun240",
      "hostname": "192.168.6.240",
      "port": 22,
      "username": "ym"
    }
  ]
}
```

要比自己解析类似：

```text
Host iyun240
HostName 192.168.6.240
User ym
Port 22
```

更适合作为 GUI 程序内部配置。

但是：

> `~/.ssh/config` 仍然应该支持导入和兼容，而不是直接拿它作为 SSH Forward 的主数据库。


# 7. config.json 总体结构

建议：

```json
{
  "version": 1,
  "settings": {},
  "hosts": [],
  "tunnels": [],
  "groups": []
}
```

不要使用 Host 内部嵌套 Tunnel 作为唯一结构。

推荐：

```text
Host
Tunnel
```

分离。

原因是后面更容易支持：

```text
一个 Host 多个 Tunnel
Tunnel 分组
Tunnel 搜索
Tunnel 排序
Tunnel 批量启停
配置迁移
```

# 9. 配置文件版本机制

一定需要：

```json
{
  "version": 1
}
```

后续配置结构改变时：

```text
version 1
    ↓
version 2
    ↓
version 3
```

启动时执行：

```text
load config
     ↓
detect version
     ↓
migration
     ↓
validate
     ↓
backup old config
     ↓
save new config
```

例如：

```text
V1

"autoReconnect": true
```

以后改成：

```text
V2

"reconnect": {
    "enabled": true
}
```

程序可以自动转换。

不能让版本升级破坏用户已有配置。

# 10. ID 设计

不能用：

```text

```

作为唯一标识。

例如用户可以存在：

```text
Jupyter
Jupyter
Jupyter
```

因此每个实体都应该有 ID：

```text
host_xxxxxxxxx
tunnel_xxxxxxxxx
group_xxxxxxxxx
```

实际推荐：

```text
UUID v4
```

例如：

```json
{
  "id": "d31fbd8b-b244-459a-9744-68b155dc29fa"
}
```

name 仅用于显示。

# 11. 密码与凭据设计

这是整个架构里很重要的一部分。

## 禁止

不要：

```json
{
  "password": "123456"
}
```

也不要：

```json
{
  "passphrase": "abcdef"
}
```

config.json 只能保存：

```json
{
  "credential_id": "cred_iyun240"
}
```

实际密码存在系统安全凭据库。

---

## Windows

使用：

```text
Windows Credential Manager
```

---

## macOS

使用：

```text
Keychain
```

---

## Linux

优先：

```text
Secret Service
```

例如：

```text
GNOME Keyring
KWallet
```

---

整体：

```text
config.json

credential_id
      │
      ▼
Credential Manager
      │
      ├── password
      └── key passphrase
```

这样复制：

```text
config.json
```

到另一台电脑，也不会泄露 SSH 密码。

# 14. 推荐 SSH Backend 策略

长期推荐：

```text
Embedded SSH Backend
```

作为默认。

原因：

```text
Windows 不依赖系统 ssh.exe
Linux 不依赖 OpenSSH 安装情况
macOS 行为一致

密码登录更容易实现
状态获取更准确
错误分类更准确
GUI 集成更自然
```

同时保留：

```text
OpenSSH Backend
```

作为高级兼容模式。

例如：

```json
{
  "ssh_backend": "embedded"
}
```

或者：

```json
{
  "ssh_backend": "openssh"
}
```

# 15. 一个 SSH Connection 对应多个 Tunnel

这是核心设计原则。

错误设计：

```text
Tunnel 1
   └── SSH Connection

Tunnel 2
   └── SSH Connection

Tunnel 3
   └── SSH Connection
```

正确设计：

```text
Host
 │
 ▼
SSH Connection
 │
 ├── Tunnel 1
 ├── Tunnel 2
 ├── Tunnel 3
 └── Tunnel 4
```

例如：

```text
iyun240
192.168.6.240
        │
       SSH
        │
 ┌──────┼────────┬────────┐
 ▼      ▼        ▼        ▼
8888   8787     3306     6006
```

```text

2 sec
4 sec

16 sec

30 sec
```

```json
{
  "reconnect": {
    "enabled": true,
    "initial_delay_ms": 1000,
    "max_delay_ms": 30000,
```

# 20. 网络恢复处理

典型情况：

```text
WiFi断开
网卡切换
VPN断开
电脑休眠
服务器重启
```

行为：

```text
CONNECTED
    ↓
SSH lost
    ↓
RECONNECTING
    ↓
wait
    ↓
SSH reconnect
    ↓
rebuild tunnels
    ↓
RUNNING
```

Tunnel 不应该要求用户手工重新启动。

推荐严格按照：

```text
01 Config 数据结构

02 Config JSON load/save

03 Config validation

04 SSH Connection

05 Local Forward

06 多 Tunnel 共用 Connection

07 Connection reconnect

08 CLI

09 Tauri GUI

10 Tray

11 Credential Manager

12 Auto Start

13 Logs

14 SSH Config Import
```

不要一开始先画大量 GUI。

最先验证的是：

```text
Core 能否稳定保持 SSH Tunnel。
```

# 75. 项目的核心边界

SSH Forward 不做：

```text
Terminal Emulator
Shell
SFTP
SCP
File Manager
Text Editor
Remote Desktop
Server Monitoring
```

只围绕：

```text
SSH Tunnel
```

这会让整个项目保持很小。

# 78. 最关键的设计决定

这个项目建议从一开始确定以下几个原则：

```text
① config.json 使用严格 JSON

② 密码绝不进入 config.json

③ 一个 SSH Connection 可以承载多个 Tunnel

④ Host 和 Tunnel 分开保存

⑤ GUI 和 CLI 使用同一套 Core

⑥ SSH Backend 抽象，不绑定单一实现

⑦ 默认只监听 127.0.0.1

⑧ 默认启用 Host Key 校验

⑨ 自动重连属于核心功能，不是附加功能

⑩ 产品只专注 SSH Forwarding
```

按照这个架构实现，后续无论增加：

```text
-R
-D
ProxyJump
Daemon
移动端
Cloud Sync
多设备同步
```

都不需要推翻现有配置格式和核心架构。
